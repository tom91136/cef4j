# cef4j engineering plan

This is the single durable record of unfinished work and settled constraints. Current architecture and usage are in
[README.md](README.md); investigation procedures and platform traps are in [DEBUG.md](DEBUG.md).

## Objective

Deliver a portable CEF distribution that supports in-process OSR and an out-of-process Remote CEF API. In the latter
mode, the JVM client survives a native server crash, can recover by constructing a new generation, and need not load
cef4j JNI libraries. Automation targets the packaged CEF through cef4j's own W3C endpoint, without a system Chrome or
ChromeDriver requirement.

## Non-negotiable constraints

1. **Java 11 remains the runtime floor.** Runtime dependencies and generated bytecode must pass the bytecode enforcer.
   A baseline increase requires an explicit decision and migration plan.
2. **The JavaFX compile baseline stays at 13.0.2 for now.** CI may test coherent newer JavaFX runtimes, but compile and
   test versions must move together and routine dependency maintenance must not raise the published baseline.
3. **The JVM is the long-lived side.** Portable runtime-server clients use standard Java/pure-Java libraries and load
   no cef4j native library. Optional UDS support may use junixsocket while Java 11 lacks the standard API.
4. **The server is CEF-aware and frontend-neutral.** It implements CEF object ownership, generated Remote CEF dispatch,
   callbacks, DevTools, and frame export directly. It does not know JavaFX, Swing, Selenium, or application policy.
5. **Remote CEF stays close to the in-process API.** Generated typed facades are primary; CDP is an additional channel,
   not the entire product API.
6. **Control and frame choices are independent.** Higher layers depend on `CefSession`/frame SPIs, never a concrete
   ZMQ, UDS, WebSocket, named-pipe, inline, or shared-file implementation.
7. **Provider code stays consolidated.** New implementation-only providers normally belong in
   `cef4j-remote-core` or `cef4j-remote-frame`; create a Maven module only for a real dependency/API boundary.
8. **Recovery never reuses native identity.** Each server start is a new generation. Old sessions, facades, handles,
   and shared-frame paths are invalid and must not be replayed.
9. **W3C outside, CDP/Remote CEF inside.** Selenium is test scope only. Unsupported WebDriver commands return standard
   errors rather than partial or invented success.
10. **Remote exposure is secure by construction.** Loopback is the default. WAN use requires TLS, authentication,
    origin/capability policy, resource limits, and an explicit trust boundary.
11. **Native/UI tests never use the active Linux desktop.** Run them in `xvfb-run`.

## Completed foundation

- Generated multi-version JNI bindings and JavaFX/Swing OSR views run on Linux, macOS, and Windows.
- `Cef` owns platform-specific lifecycle defaults and composes registered generated `CefApp` handlers.
- Dependency/plugin warnings were reduced while preserving Java 11 runtime bytecode checks; JavaFX was deliberately
  left unchanged.
- Remote core/API/frame/JavaFX/Swing, native-server, and WebDriver boundaries are present.
- ZMQ, optional UDS, WebSocket, Windows named-pipe local control, inline frames, and shared-file frames are implemented.
- Transport/session and generated protocol were consolidated into `cef4j-remote-core` and `cef4j-remote-api`.
  JSON-library boundaries remain optional adapters: CDP, Remote CDP, recording, and WebDriver provide symmetric Gson
  and Jackson choices while shared lifecycle and automation code remains JSON-library-neutral. Frame and UI toolkits
  remain independent optional boundaries.
- Packaged-runtime, provider, Selenium, and cross-backend tests are centralized in `cef4j-integration-tests`.
- The packaged `cef4j-runtime-server` exports a versioned generated Remote CEF API and raw CDP channel. A separate
  Java-11 `cef4j-cdp` boundary supplies the exact Chromium/V8 schema, generated immutable domain models/clients,
  codec SPI, fingerprint, opt-in exact-version check, and raw escape hatch over both remote and in-process transports;
  schema refresh is source-derived and never launches CEF.
- The bootstrap handshake rejects protocol/API/provider mismatches before session creation.
- `RuntimeServerSupervisor` performs bounded restart with generation isolation and keeps the Java client alive.
- Composable `CefSessionMiddleware` includes codec-pluggable, versioned NDJSON logical API recording and strict
  immediate/timed/manual replay;
  per-generation traces reproduce requests, events, intercepts, failures, and concurrency without CEF or a transport.
- Raw BGRA/JPEG codecs, a per-stream codec SPI with delta-chain metadata, and an MJPEG HTTP representation exist.
- WebSocket control supports bearer credentials and Java-side TLS trust; remote binding remains opt-in.
- WebDriver M0/M1 and a useful part of M2-M4 are implemented. Raw HTTP and unmodified Selenium cover navigation,
  script, screenshot, elements/state/staleness, click, clear/send keys, cookies, refresh, and timeouts.
- In-process and runtime-server WebDriver adapters share the same command engine; Selenium smoke coverage exercises
  both without Chrome or ChromeDriver.
- Packaged integration has exercised ZMQ + shared-file, WebSocket + inline, and UDS + inline paths, with CDP evaluated
  over more than one control provider.
- CI runs CEF 109/116/144/146 across Linux, Windows, and macOS on both x86-64 and ARM64, plus curated JDK/JavaFX lanes, including JDK 11 runtime
  forks. Linux builds use cached AlmaLinux 8 sysroots to hold the glibc floor at 2.28; the unused RISC-V definition
  remains available without adding a required matrix lane. Release automation produces platform-neutral Java artifacts, six classified native/runtime-server bundles,
  GitHub Release assets, and seven size-safe review-before-publish Maven Central deployments. OS-family
  classifiers avoid unwanted native downloads; `*-all` POMs aggregate every supported platform when desired.

## Workstream 1: WebDriver conformance

Finish WebDriver Classic before considering BiDi.

### Elements (M2)

- complete CSS, link text, partial link text, tag name, and XPath behavior;
- nested find and active element edge cases;
- align element identity and stale detection with document/context replacement;
- complete attribute/property/CSS/text/rect/displayed/enabled/selected semantics;
- cover JSON clone rules for element references and cyclic/unsupported results.

Exit gate: a pinned, documented WPT/wdspec element allowlist plus Selenium element flows pass on all packaged
platforms.

### Interaction (M3)

- complete click scrolling, center-point hit testing, interception, and bounds behavior;
- support standard WebDriver special keys in send-keys;
- implement the W3C Actions input-source state machine for key, pointer, and wheel sources;
- implement release-actions cleanup and per-session input state;
- expose viewport/window rect only when semantics are consistent with OSR and device scale.

Exit gate: Selenium form/action flows and selected interactability/actions specs pass on Linux, macOS, and Windows.

### Context and browser state (M4)

- window handles, new/close/switch window;
- child-frame and parent-frame switching;
- alerts, prompts, and before-unload behavior;
- back/forward completion and page-load strategies;
- explicitly implement or reject print, downloads, and unsupported native-window operations.

Cookies, refresh, and timeout configuration already have a working vertical slice; expand their standards/error cases
rather than reimplementing them.

### Operations/conformance (M5)

- pin a WPT revision and maintain a machine-readable allowlist/exclusion file with reasons;
- add Selenium Java and Python black-box suites;
- test malformed/oversized requests, command limits, disconnects, timeouts, and runtime crashes;
- document Grid registration and secured deployment;
- investigate WebDriver BiDi only after Classic has a stable conformance baseline.

## Workstream 2: Recovery semantics and client UX

- add a high-level recovery coordinator that rebuilds browser/window state from the supervisor generation callback;
- define what state is application-owned and replayable: URLs, viewport, subscriptions, and selected configuration;
- keep native object handles, JS object IDs, DOM nodes, callbacks, and codec dependency chains non-replayable;
- decide and document WebDriver behavior on runtime loss. The conservative default is to fail the active command and
  invalidate the WebDriver session; transparent browser recovery may be a separate opt-in capability later;
- stress crash loops, startup failure, cancellation, close-during-restart, and backoff reset after stability;
- verify all transport and shared-frame resources close promptly and stale generation files are eventually reclaimed;
- add recovery integration coverage for JavaFX/frame consumers and MJPEG source reattachment.

Exit gate: repeatedly killing the server cannot crash or wedge the JVM, leak pending calls, reuse a handle/path, or
deliver an old-generation event after the replacement becomes active.

## Workstream 3: Transport and frame completeness

The intended provider set is:

- **local:** Unix defaults to pure-Java loopback ZMQ; Windows uses a named pipe. Explicit UDS remains available on Unix.
- **zmq:** cross-platform high-performance/compatibility option.
- **websocket:** interoperable and remote-capable control option.
- **inline:** complete-frame portable fallback.
- **shared-file:** cross-platform local frames using `FileChannel.map`-compatible files.

Next work:

- benchmark latency, throughput, allocation rate, copy count, and crash cleanup by platform/provider combination;
- make negotiated message/frame limits and backpressure behavior explicit;
- load-test WebSocket fragmentation, reconnect, slow readers, and bounded queues;
- harden named-pipe cancellation/close and Windows mapped-file cleanup;
- compare explicit UDS with local ZMQ on Linux/macOS before changing the portable default;
- publish a small custom codec example, including state reset, key-frame requests, base-sequence validation, and
  recovery behavior;
- retain MJPEG as the browser-compatible stream. Do not add a built-in video-codec subsystem; applications may supply
  codecs through the frame SPI.

## Workstream 4: WAN hardening

- provide a reference reverse-proxy/tunnel configuration for WebSocket control and WebDriver HTTP;
- specify bearer/token rotation, TLS trust, origin policy, allowed capabilities/runtime arguments, and profile policy;
- enforce request, script-result, screenshot, frame, pending-command, connection, and rate limits;
- fuzz envelope/WebSocket/HTTP parsing and reject unknown bootstrap capabilities safely;
- test induced latency, packet loss/disconnect, bandwidth limits, slow MJPEG consumers, and reconnect storms;
- keep raw Remote CEF and CDP private by default; prefer an authenticated WebDriver gateway when broad CEF authority is
  unnecessary.

Exit gate: no listener becomes non-loopback without explicit configuration and the required authentication/TLS policy.

## Workstream 5: Public API cleanup

The old initialization refactor document was only partially carried out. Current code has centralized lifecycle,
platform-correct `Cef.osrLaunchArgs()`, active-settings validation, and composable generated handlers, but
`CefWebView.initialise/terminate` and `CefBrowserPanel.initialise/terminate` remain public compatibility entry points and
view constructors still require prior initialization.

Before changing that API:

- decide whether explicit initialization is preferable to lazy initialization, particularly on macOS Thread 0;
- if removing toolkit statics, provide a source-migration note and decide whether to deprecate for one release;
- do not silently choose shared cache/profile paths during lazy construction;
- retain cross-toolkit OSR settings validation and handler registration before initialization;
- keep runtime-server client lifecycle separate from the singleton in-process `Cef` lifecycle.

This is a deliberate API decision, not required runtime-server work.

## Workstream 6: Dependencies and Java floor

- keep Maven Enforcer bytecode checks on every distributable module and runtime dependency;
- run the focused Java 11 runtime smoke lane whenever dependencies, generated code, or packaging changes;
- isolate build-only Java 17+ tooling from runtime artifacts;
- evaluate upgrades in small groups and remove warnings at their source;
- reject dependencies that require Java >11 unless an equivalent Java 11-compatible choice exists or the project
  explicitly approves raising the floor;
- discuss JavaFX separately at the end of dependency work; do not update it as part of routine bumps.

## Verification gates

For each completed slice:

1. `git diff --check` and documentation/reference checks.
2. Spotless, Error Prone/NullAway, SpotBugs, and Java 11 bytecode enforcement.
3. Unit and fake-backend tests before native integration.
4. Linux native/UI tests under `xvfb-run`; never on the active display.
5. Packaged runtime-server tests with fresh profiles and local deterministic pages.
6. Relevant provider combinations, including one non-default control and frame path.
7. Linux, macOS, and Windows verification for platform-sensitive changes.
8. Crash/restart verification whenever session, process, transport, frame, or automation lifecycle changes.
